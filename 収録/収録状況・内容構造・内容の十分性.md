# 収録状況・内容構造・内容の十分性

収録状況、内容構造、内容の十分性を別の判定軸として扱います。

目的は共通の基盤や点数を作ることではありません。各リポジトリの既存スキーマ、読み込み処理、検証器、テスト、ドメイン基準を使い、機械で確定できる失敗と、内容を読まないと判断できない不足を分けます。

## 収録状況を導出する

列挙・分類できる収録対象について、「何を収録対象とするか」という収録設計と、実際に存在する収録物の対応から現在の収録状況を導出します。

例:

- 収録対象IDの重複
- 収録対象なのに収録物が存在しない
- 収録物があるのにどの収録対象にも接続されない
- 分類体系 / 学習体系 / マニフェスト / リリース対象範囲等、収録対象を定める参照関係の切れ
- リリース対象条件で必須な収録対象の欠損
- 生成処理 / 実行時処理が収録対象を特定する参照関係の不整合

欠損、孤立、不整合等は収録設計と収録物から導出します。不足一覧を別のMarkdownやSkillへ手入力して保存しません。

収録物内部のスキーマ、必須メタデータ、資料 / 根拠 / 関係等の決定的な条件は収録状況へ含めず、内容構造として扱います。

## 内容構造を検証する

収録対象として存在する収録物が、内容を読まなくても確定できるスキーマ・必須メタデータ・参照関係等の条件を満たしているか、決定的に検証します。

例:

- スキーマ違反
- 必須メタデータの欠損
- IDの重複
- 資料 / 根拠 / 関係の未解決参照
- 必須の関連成果物が存在しない
- 生成元と生成物の決定的な不整合
- 公開 / リリース時の必須フィールド欠損

内容構造の検証に成功しても、収録状況や内容の十分性まで成立しているとは限りません。件数が多い、文章が長い、項目が埋まっている、といった代理指標だけで内容の十分性を判定しません。

## 内容の十分性を監査する

文章の十分さ、学習上の有効性、選択判断の有用性、安全上の説明品質など、内容を読まないと判断できないものは、ドメイン固有の基準に照らして監査します。

既に収録対象として定義されている内容を充足する手順は `../skills/content-sufficiency-fill/SKILL.md` が管理します。収録対象そのものを追加、削除、再分類、整理する場合は `../skills/content-selection-update/SKILL.md` の責務です。

## 機械可読な検証結果

検証器や収録状況を出力するコマンドがAIや別ツールから読む機械可読出力を持つ場合は、リポジトリの既存スキーマと命名を優先します。この文書を理由に全リポジトリ共通のフィールド名や結果スキーマを新設しません。

必要に応じて、失敗の種類、対象記録やパス、問題箇所、関連記録、人が読める説明、観測時点等を機械的に追えるようにします。既存の出力で十分なら第二の形式へ変換しません。

検証結果は収録物から導出する派生結果です。完了 / 未完了一覧や作業進捗として保存しません。内容の十分性を機械可読な検証結果へ無理に変換しません。

リポジトリ横断で収録対象を読む必要が実際にある場合も、既存の収録設計から必要最小限の表示用情報を導出します。その表示用情報を新しい収録設計の管理元にはしません。

## 実装原則

- 既存のスキーマ、読み込み処理、解析処理、生成処理があるならその解釈を再利用する
- 同じデータを読む第二の解析処理や、別の意味を持つ検証を重複して作らない
- 検証器 / テストは決定的な失敗だけを扱う
- 通常の検証はローカルで実行できる形を優先し、ネットワーク、LLM API、GitHub Actions、遠隔ビルドを成立条件にしない
- 収録状況を出力するコマンドは、複数ファイルの結合や探索を毎回繰り返すなど、実際の探索コストが高い場合だけ追加する
- 生成報告を定義・要求・設計の管理元へ昇格しない。必要なら毎回再生成できる表示用情報として扱う
- 共通の単一点数、中央ダッシュボード、全リポジトリ共通の検証器パッケージを先に作らない

## リポジトリごとの実装は揃えなくてよい

Goの検証器、Nodeのスクリプト、Astro / TypeScriptのテストなど、実装技術はリポジトリに合わせます。

共通化するのはコマンド名や基盤ではなく、次の責務です。

1. 収録設計と収録物の対応から収録状況を導出できる
2. 収録物が内容構造上の条件を満たすか決定的に検証できる
3. 内容の十分性を、内容を読んで監査できる
4. 検証・監査結果から次に対応する有限な変更単位だけをIssueへ送れる

同じ検証処理そのものが複数リポジトリで繰り返し保守負担になってから、共通パッケージ化を検討します。

## AIエージェントからの使い方

AIエージェントは、利用可能な決定的検証がある場合は先にその結果を使い、既に機械で判定できる不整合を手作業で再調査しません。

検証で不足が見つかったら、必要な収録物だけを読みます。内容の不足まで確認する必要がある場合だけドメイン基準による監査へ進みます。

検証結果自体を進捗台帳にはせず、実施すると決めた有限作業だけをIssueで管理します。
