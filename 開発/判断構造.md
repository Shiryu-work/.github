# 判断構造

リポジトリ内の判断が、どの責務からどの責務へ具体化されるかを管理します。語の定義は `用語.md` を参照します。

`プロダクト/哲学.md` を最上位の判断基準とします。そこから、プロダクト固有の意味と、複数場面で使う判断規則へ分かれます。

```text
                  プロダクト/哲学.md
                    /          \
                   ↓            ↓
        プロダクト/定義.md    各領域の原則
                   ↓            ↓
        プロダクト/要求.md ← 方針・規約
                   ↓            │
             設計/概要.md ←─────┘
                   ↓
      コード / スキーマ / データ / 設定
                   ↓
                 検証
```

プロダクト定義は目的・利用者・対象範囲を具体化します。原則・方針・規約は、要求や設計を判断するときの基準として使います。

下位は上位を具体化できますが、実装都合で上位の意味を暗黙に弱めたり置き換えたりしません。上位判断を変えるなら、その管理元を更新します。

## 現在仕様と履歴を分ける

現在仕様の管理元には、現在採用している意味・要求・設計を直接書きます。過去Issue / PR、移行工程、削除済みパスを理解しないと現在仕様を読めない状態にしません。

比較した案、捨てた案、変更経緯はIssue / PR / Git履歴へ残します。現在も効く制約だけを現在仕様へ書き戻します。

## 意図と実物を混同しない

哲学・要求・設計は「どうあるべきか」、コード・スキーマ・データ・設定は「現在どう実装されているか」を示します。食い違いは一方を自動的に正とせず、不整合として扱います。

## 必要な層だけ変更する

設計を変えても要求が変わらないなら要求を儀式的に編集しません。実装だけのリファクタリングで設計上の意味が変わらないなら設計を更新しません。
