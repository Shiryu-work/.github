# Issue運用

GitHub Issueは、人間とAIが有限の作業を扱う入口です。Issueへ現在仕様や業務状態を過剰に保存せず、何を得たら閉じられるかと、現在誰が次の操作を行えるかを管理します。

## 成果型

Issueは、何を得たら閉じられるかで次の3種類に分けます。

- `タスク: ` — 何かを実現・変更することが成果
- `考察・判断: ` — 材料と選択肢を考察し、採用・見送り・保留等の判断を確定することが成果
- `資料: ` — 比較、調査、時点付き情報等、後から参照する有限な記録を残すことが成果

タイトル接頭辞は人間向け表示です。自動化や検証処理の機械契約にはしません。作業分類、優先度、振り分けとは別軸です。

## 判断の記録

プロダクトや実装について選択肢を比較して決めた場合、判断理由・比較した案・捨てた案・残る不確実性は `考察・判断` Issueへ残します。

現在仕様を表す文書・コード・設定には、現在有効な結論とその運用に必要な情報だけを反映し、判断に至る経緯を重複保存しません。後から判断の経緯を参照する必要がある場合は、現在仕様側から該当IssueまたはPRを参照します。Issueを現在仕様の第二の管理元にはしません。

## Issueの状態

Issueの生存状態はGitHub標準のOpen / Closedを使います。

- Open — 未完了
- Closed — 成果成立、不要、重複等により終了

`完了`、`保留`、`未整理`、`後回し`等を追加の状態ラベルとして増やしません。

## AI実行許可

AIが読む実行状態は次の2ラベルだけです。

- `AI:着手可能` — AIが現在、自律着手してよい
- `AI:進行中` — AIが現在、意味のある次操作を実行中

Open Issueはこの2ラベルを同時に持ちません。

対象Issueが明示されていない場合、AIは `AI:進行中`、次に `AI:着手可能` のIssueから選びます。どちらも無いOpen Issueへは自律着手しません。利用者が対象Issueを明示した場合は、このラベルがなくてもその依頼を優先します。

実作業を始めるときは `AI:着手可能` を `AI:進行中` へ置き換えます。現在AIが進められる次操作がなくなったらAI実行ラベルを外します。

`AI:進行中` は実際の作業中だけに使います。親Issue、待ち行列、将来待ち、人手待ち、阻害待ちを惰性で進行中にしません。

## 人手待ち

人間にしかできないプロダクト判断、責任判断、権限操作、原本提供等が現在の唯一の次操作である場合は `要人手` を使います。

`要人手` が付いたIssueには `AI:着手可能` / `AI:進行中` を重ねません。人間側の操作が終わり、AIが再び実行可能になった時点で必要なAI実行ラベルを付けます。

## 阻害関係

Issue間の阻害関係はGitHub標準の `blocked by` / `blocking` を使います。阻害要因しか次操作がないIssueにはAI実行ラベルを付けません。

本文や別ラベルへ第二の依存関係台帳を作りません。

## 作業分類

作業分野の分類は成果型・AI実行許可と別軸です。振り分けに価値がある場合だけ使います。

候補は次です。

- `分類:調査`
- `分類:開発`
- `分類:保守`
- `分類:基盤`

詳細分類が不要なら付けません。`分類:調査` だから `資料`、`分類:開発` だから `タスク` とは限りません。

## 新規Issue

新規IssueはOpenかつAI実行ラベルなしで作成します。Issue作成そのものをAIへの自律実行指示とはみなしません。

整理または明示的な実行判断の後で、必要なAI実行ラベルだけを付けます。
